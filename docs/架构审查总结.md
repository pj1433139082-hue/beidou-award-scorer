## 二、修掉的三个正确性缺陷

这三条不是「代码不好看」，是**会产生错误输出**。

### B1 · 第二套 cap 表

`score.py:63` 注释写着「代码里不再有第二套常数」，`score.py:75` 的兜底值就是第二套表。

```python
# 改前
return {"A":1.0,"B":0.75,"C":0.5,"D":0.2}.get(grade, 0.5)

raise RubricError("评分卡缺少证据等级的 cap")
```

## 三、四个 deepening 候选

### 候选 1 · MaterialRecord（v3.0.0）

**问题**：5 个模块各自扫描 score.json，对「用什么标识一份材料」给不出统一答案：

```
export_xlsx.py   键 = 文件名 stem
export_docx.py   键 = 文件名 stem
modes.py         键 = 正文 name，或 stem
consistency.py   键 = 正文 name，或 stem
isolate.py       键 = 正文 name，缺了就崩
```

**物证**：modes.py 已经为此打了模糊匹配补丁 `k in name or name in k or k[:12]==name[:12]`。
**补丁的存在就是键不统一的证据。**

**做法**：一个模块拥有 shape、身份规则（ADR-0003）、缺失语义、三个下划线字段。

**踩的坑**：`as_row()` 一开始返回 `_advice`，但 export_xlsx 全程读 `_items`。结果 Word 有 3 条建议、Excel 0 条。
**这正是 MaterialRecord 要防的漂移，在迁移过程中又发生了一次**——区别是断言抓住了。

### 候选 2 · AdviceSheet（v3.1.0）

**问题**：写入端按维度数算列（`COL_ORIG = COL_AFTER + 1`），读取端却在猜（`row[9]`）。而 9/10/11 只在维度数恰好 5 时成立。

**已发生的 drift**：modes.py 直接索引 `row[9]`，check_compliance.py 用 `_col(row, 9)` 有越界保护。

**做法**：列位置、编号格式、表头名全部单一定义。read() 按表头反查，维度数变了也不用改偏移。

### 候选 3 · CheckCatalog（v3.2.0）—— 发现真 bug

**问题**：5 张按 check id 索引的平行表，长度互不相等（RULES 18 / HINTS 13 / CHECKS 20），用 `.get()` 兜住差异。

**发现**：`C01` 和 `C10` 在 CHECKS 里有、在 RULES 里没有。而 `build_items()` 是 `if not rule: continue`——**静默跳过**。

**真实影响**：

```
19 份材料里 C01 warn/fail 2 份、C10 warn/fail 1 份
这 3 份完全丢失建议
而 _global_points 给 C01 打了 3.0（全表最高权重）——从未真正用过
```

修完后建议条目 **72 → 73**。

### 候选 4 · strict 覆盖（v3.3.0）

**问题**：`--strict` 控制 6 处退出码，**一条都没测**。这个文件改了 17 次（全项目最多）。

**覆盖时发现的行为**：非严格模式下，全无评分时**仍然返回 2**——这是对的行为，但从未写下来。

## 四、跳过的候选及理由

**候选 5 · batch.py 收窄 15 个开关** —— 按分析跳过。

子智能体的 deletion test 结论是「合并只搬复杂度，不集中它」。而 subprocess 隔离本身有价值：单份材料抽取失败不拖垮整批、`--from-json` 断点续跑依赖它。

## 六、核心教训

### 1. 注释与代码矛盾，以代码为准会产生错误

`score.py:63` 的注释描述了一个**已经做完但没做完**的修复。读注释会以为问题解决了。

### 2. `.get()` 让「漏写」和「本来没有」无法区分

CheckCatalog 的核心价值不是「一张表代替五张」，而是 `require()` 会在缺定义时报错。旧的 `.get()` 把遗漏变成了 no-op。

### 3. 模糊匹配掩盖问题直到它真正出错

modes.py 的 `k[:12] == name[:12]` 让 19/19 看起来很健康，实际上键是不统一的。删掉它才暴露真相。

### 4. 断言抓住的是重构过程中新引入的问题

MaterialRecord 迁移时引入的 `_advice` vs `_items` 错误，是 verify_format 抓住的。**没有断言，这个会直接进生产。**

### 5. `str.replace` 是本会话最大的操作风险

三次未验证的 `str.replace` 静默吃掉代码块，其中一次把 selftest_pipeline.py 的 `main()` 和入口点整个删掉了（47791 → 42905 字符）。

**规则**：任何结构性编辑之后必须验证文件长度和尾部内容，否则这个编辑不算完成。
