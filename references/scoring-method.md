# 评分方法实现细节

## 1. 证据分级（A/B/C/D）

证据等级不看"写得多漂亮"，看**能不能被别人按同一口径重算**。

| 等级 | 名称 | 判定标准 | cap | 分档区间（rubric，左闭右开） |
|---|---|---|---|
| A | 可复算 | 系统截图 + 运营日志/成本台账 + 独立验证记录；别人拿同样数据能算出同一个数 | 1.00 | [0.75, 1.00] |
| B | 部分佐证 | 有佐证材料，但口径没闭合（缺时段/缺项目/缺基线） | 0.75 | [0.50, 0.75) |
| C | 自述 | 只有文字、PPT 结论、自评表 | 0.50 | [0.20, 0.50) |
| D | 无佐证 | 只有目标/规划，或数据找不到出处 | 0.20 | [0.00, 0.20) |

> **分档必须互不重叠**。原设计是 A[0.70,1] / B[0.45,0.75] / C[0.15,0.5] / D[0,0.2]，0.72 同时落进 A 与 B——
> 这是非法 rubric。现已改成上面的左闭右开区间，并由 `score.py: validate_rubric_bands()` 在启动时自检，交叠即报错退出。
> 依据：deepeval `g_eval/utils.py:212 validate_and_sort_rubrics`（逐对检查区间重叠即报错）。

**引文核验会反向压低等级**（`score.py: grade_cap`）：

| 通过核验的引文数 | 最终等级 |
|---|---|
| 0 条 | D（无论自称什么等级） |
| 1 条 | 最高 C |
| ≥2 条 | 采纳自称等级 |

因此"自评 A 但拿不出两句原文"的维度，最多拿到满分 50%。

## 2. 机检 → 维度的封顶映射

`apply_machine()` 把 `checks.json` 的 warn/fail 翻译成上限，同维度多条闸门取**最严**的那条。

| 机检项 | 状态 | 作用于 | 上限 |
|---|---|---|---|
| C02 已实现/在研分离 | fail / warn | value | 0.40 / 0.75 |
| C03 基线可算性 | warn | value | 0.85 |
| C04 效益佐证覆盖率 | fail / warn | value | 0.70 / 0.85 |
| C11 模型实验室证据 | fail / warn | intelligence | 0.40 / 0.70 |
| C12 产品就绪度 | warn / fail | readiness | 0.65 / 0.45 |
| C14 创新性对照 | fail / warn | novelty | 0.60 / 0.80 |
| C15 战略对齐与卡点 | warn | usability | 0.80 |
| C16 真实性软信号 | warn | value | 0.85 |
| C13 成果迭代性（仅金火炬） | fail | iteration | 一票否决 |

状态为 `na` 的检查**不产生任何约束**——不要为了"跑满检查项"去凑。

## 3. 固定扣分

| 编号 | 扣分 | 触发 |
|---|---|---|
| D1 重复计入 | -3 | C08 检出同一金额多处出现 |
| D2 数字对不上 | -2 | C05 变化率自述与复算偏差 >5pp |
| D3 基线缺失 | -2 | 已折进 C03 的封顶，不重复扣 |
| D4 截图缺失 | -2 | C17 全文无图片/截图 |
| 占位符残留 | -2 | C09 检出下划线/XXXX/（文本） |

扣分作用于小计，不会让单项分数变负；最终分下限为 0。

## 4. 计分公式

```
维度最终分 = min(评审员自评, 满分 × 封顶系数)  ，若证据等级被下调再取 min(…, 满分 × 等级系数)
小计       = Σ 维度最终分
AI 评分    = max(0, 小计 − Σ 固定扣分)
综合评分   = 0.75 × 现场分 + 0.25 × AI 评分      （金火炬不适用）
```

**为什么不直接乘系数**：如果对没降级的维度也乘 A=1.0 的系数，等于什么都没做；只有降级时才收缩，才能既保守又不惩罚证据齐全的材料。

## 5. 争议判定的三条来源

1. **机检 warn/fail**：结构性问题（缺表、缺佐证、缺基线）。
2. **引文核验失败**：评审员写了原文里没有的话——这是最危险的一类，必须进清单。
3. **评审员主动标记**：拿不准的、跨口径的、需要答辩确认的。

三类合并成 `disputes` 写进 `report.md` 第四节，对应官方 P12「争议问询反馈机制」。

## 6. 置信度

| 置信度 | 触发条件 |
|---|---|
| 高 | 机检 warn+fail < 6，且所有维度证据等级 ≥ B |
| 中 | warn+fail ≥ 6，或有维度落在 C/D |
| 低 | warn+fail ≥ 9 |

置信度是给读者判断"要不要人工复核"用的，**不是分数的一部分**。

## 6.5 未评分维度（不要把"没读到"记成"差"）

judgments 里某维度 `score` 缺失或为 `-1`，该维度进 `unscored`：

- **不参与**小计与分母，剩余维度按比例折算回百分制（便于跨材料比较）；
- `report.md` 单独列出「未评分维度」并写明原因（`unscored_reason`）；
- 理由：把"抽取器没读到"记成"申报书差"，是评分技能最致命的错。
  依据 ossf/scorecard `checker/check_result.go:40 InconclusiveResultScore = -1` 与 `pkg/scorecard/scorecard_result.go:83 GetAggregateScore` 的 `continue`（排除出分母，而非计 0 拉低均值）。

## 7. 确定性

同一份 `doc.json` + `checks.json` + `judgments.json` 重复运行，`score.json` 数值完全一致（无随机、无时间戳、无网络）。这就让"为什么是这个分"可以被逐行重算。

## 8. 设计取舍

- **不接 LLM API 端到端打分**：不可追溯、不可离线、成本不可控，且无法解释"为什么扣这 3 分"。改成"脚本算硬指标 + 评审员写带引文的判断"，把不可解释的部分压缩到最小。
- **机检宁多勿少，但都要能被推翻**：每条检查都输出 `evidence`（表N/行M 或原文片段），人工一眼能回原文核对。
- **分值硬编码进 rubric.json**：官方一旦改标准，只改这一个文件，脚本不用动。
